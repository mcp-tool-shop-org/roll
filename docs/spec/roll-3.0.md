# Roll 3.0 design specification

*Status and conventions:*
- This is the design basis for Roll 3.0: a Rust core (`crates/roll-core`) that is the single source of truth, with `@mcptoolshop/roll` rebuilt as a pure TypeScript port verified against fixtures generated by the core. Section numbers are stable; code comments cite them.
- The 2.x reference tree is PR #11's head `719174717254762e2c1f235fb73792a46fa55995` (shipped as `@mcptoolshop/roll` 2.1.2, on top of `main` `256a911`). Unless another commit is named, every `path:line` citation of the 2.x code is at that commit.
- Every claim about an external Rust crate's version, licence, Cargo features, API or internals is marked **`(read at source: <URL>, v<version>)`** or **`[Guess]`**.
- Statements about how the XRPL Testnet trading game *Merchant League* will use the engine are design assumptions, marked **`[Guess]`** where they go beyond its published design.

## 1. Crate layout

### 1.1 Workspace structure and safety invariants

Roll 3.0 is organized as a single Cargo workspace (`edition = "2024"`, `rust-version = "1.88"`, matching the MSRV of `sha2` 0.11.1 and `proptest` 1.12.0; local toolchain verified at `rustc 1.98.1`) alongside the npm package `@mcptoolshop/roll` (see Section 7):

```text
crates/
  roll-core/   # Pure deterministic library: parser, AST, PRNG/KDF, pipeline, receipts, analyzer, tables
  roll-cli/    # Terminal binary (`roll`): rolling, analysis, table ops, receipt verification, fixture export
  roll-mcp/    # Optional thin stdio MCP binary (`roll-mcp-rs`) over roll-core for Node-free studio workflows
```

**Zero-`unsafe` rule:** The workspace root `Cargo.toml` sets:

```toml
[workspace.lints.rust]
unsafe_code = "forbid"
```

Every workspace crate sets `[lints] workspace = true` and `#![forbid(unsafe_code)]` at `src/lib.rs` / `src/main.rs`. No `unsafe` block, `unsafe fn`, or `unsafe impl` is permitted anywhere in `roll-core`, `roll-cli`, or `roll-mcp`.

**Purity of `roll-core`:** `roll-core` is `#![no_std]`-compatible using `extern crate alloc` (with an optional default `std` feature solely for implementing `std::error::Error` — though `core::error::Error` is stable on `rust-version = "1.88"`). `roll-core` performs **zero** filesystem I/O, network I/O, environment-variable reads, wall-clock queries, or OS CSPRNG syscalls, and never uses `HashMap` / `HashSet` (`RandomState`). Consequently, `roll-core` compiles unchanged to `x86_64-pc-windows-msvc`, `x86_64-unknown-linux-gnu`, `aarch64-apple-darwin`, `wasm32-unknown-unknown`, and `wasm32-wasip1`.

## 2. The PRNG and roll addressing

### 2.1 Generator choice: `ChaCha12Rng` (`rand_chacha` 0.10.0)

Roll 2.x's `seededRng` (`src/engine/random.ts:11-19`) is unsuitable for player-auditable gameplay on three counts:
1. `let state = seed | 0;` (`src/engine/random.ts:12`) truncates 53-bit CLI/JSON integers to signed 32-bit (`seed = 1` and `seed = 4294967297` produce identical streams, and `NaN | 0 === 0` in Bridge at `src/bridge/handler.ts:136`).
2. `mulberry32` has only $2^{32}$ internal states (cannot even generate all $20! \approx 2.43 \times 10^{18}$ permutations of 20 items) and is trivially invertible from two outputs.
3. Range scaling uses IEEE-754 float division `/ 4294967296` and `Math.floor(raw * (max - min + 1))` (`src/engine/random.ts:17-18`), introducing modulo bias for any `span` not dividing $2^{32}$.

**Choice:** Roll 3.0 standardizes on **`ChaCha12Rng`** from `rand_chacha` `0.10.0` (`read at source: https://docs.rs/crate/rand_chacha/0.10.0/source/src/chacha.rs, v0.10.0`):
- **Why ChaCha over `Xoshiro256**` / `Pcg64Mcg`:** In *Merchant League*, turns resolve from public randomness (`drand` rounds) with public route histories. A cryptographic stream cipher keyed by a 256-bit digest guarantees zero state-recovery or cross-coordinate correlation, natively provides a 256-bit seed (`[u8; 32]`), 64-bit block counter (`set_word_pos`), and 64-bit stream ID (`set_stream`), and consists solely of 32-bit `u32` add-rotate-xor (`ARX`) operations (`src/guts.rs:43-52`), which port in ~30 lines of exact integer code to TypeScript.
- **Why 12 rounds (`ChaCha12Rng`) over 8 or 20:** Published academic differential-linear distinguishers reach 7–7.5 rounds of ChaCha; `rand_chacha` `0.10.0`'s own crate documentation (`src/lib.rs:26-28`) recommends `ChaCha12Rng` (6 double-rounds, `src/chacha.rs:211-217`) where unpredictable cryptographic strength is desired, providing a 5-round security margin at negligible cost (one 64-byte ChaCha12 block yields eight `u64` draws, covering a typical dice or table roll in a single block refill).

### 2.2 Roll addressing (`RollAddress`) and SHA-256 key derivation

Threading a single mutable sequential RNG across a campaign (as `BridgeHandler.rng` does at `src/bridge/handler.ts:48`) makes isolated verification impossible: any UI preview, unrelated town market check, or mid-season table edit shifts every subsequent roll, forcing a player to replay from Turn 1 to check Turn 50.

Instead, **every roll is statelessly addressed** by a 6-tuple `RollAddress`:
1. **`campaign_seed: SeedMaterial`** — either `Int64(i64)` (all $2^{64}$ signed 64-bit integers remain distinct, fixing `seed | 0`) or `Bytes32([u8; 32])` (for 256-bit `drand` round randomness or campaign master seeds in *Merchant League*).
2. **`turn: u64`** — discrete turn / market day index (`0` for standalone CLI/npm calls).
3. **`domain: String`** — non-empty UTF-8 namespace (`1..=128` bytes; ASCII printable `[!-~]` enforced, e.g. `"road_event"`, `"market_shock"`, `"cli"`).
4. **`entity_id: String`** — UTF-8 subject identifier (`0..=256` bytes, no control chars; e.g. caravan ID, town ID, XRPL account, or `""` for unattached rolls).
5. **`roll_index: u64`** — 0-based counter disambiguating multiple rolls within the same `(campaign_seed, turn, domain, entity_id)`. In `roll --times N`, roll $i \in 0..N$ uses `roll_index = base + i`, so roll #7 is independently verifiable without rolling #0..#6. In `roll_table_multiple` without replacement, all `count` coupled draws share a single `roll_index` and one `RollReceipt`.
6. **`rules_version: String`** — non-empty ASCII version string (`1..=64` bytes; default `"roll.v3"`), cryptographically binding the RNG stream to the rule specification.

**Hash choice (`SHA-256` via `sha2` 0.11.1 over `blake3` 1.8.7):**
- `blake3` 1.8.7's `build.rs` (`lines 337-338`, `read at source: https://docs.rs/crate/blake3/1.8.7/source/build.rs, v1.8.7`) invokes `cc::Build` to probe `cl.exe` / AVX-512 flags on `x86_64` even when `features = ["pure"]` is enabled, emitting C-compiler warnings on bare Windows Rust installs, and `blake3` is absent from Node.js `node:crypto` (verified on local Node `v26.13.1`: `crypto.getHashes()` includes `sha256` and not `blake3`).
- `sha2` 0.11.1 sets `build = false` (`read at source: https://docs.rs/crate/sha2/0.11.1/source/Cargo.toml, v0.11.1`), aligns with XRPL's `PREIMAGE-SHA-256` escrows and `drand` randomness digests, and is available in standard libraries of Node.js, WebCrypto, Python, Go, and OpenSSL so any player can verify a receipt with zero third-party packages.

**Exact KDF byte framing (`derive_roll_key`):**
All variable-length strings are length-prefixed with 4-byte little-endian `u32` lengths so the framing is **strictly prefix-free (injective)** — no two distinct `RollAddress` values can ever produce the same byte preimage:

```text
derived_key: [u8; 32] = SHA-256(
    b"roll.v3.seed_kdf\x00\x01"                 // 18-byte protocol tag + KDF version 0x01
 || match campaign_seed {
        Int64(n)   => [0x01u8] || n.to_le_bytes()   // 1 + 8 = 9 bytes (two's-complement LE)
        Bytes32(b) => [0x02u8] || b                 // 1 + 32 = 33 bytes
    }
 || turn.to_le_bytes()                          // 8 bytes LE
 || (domain.len() as u32).to_le_bytes()         // 4 bytes LE
 || domain.as_bytes()
 || (entity_id.len() as u32).to_le_bytes()      // 4 bytes LE
 || entity_id.as_bytes()
 || roll_index.to_le_bytes()                    // 8 bytes LE
 || (rules_version.len() as u32).to_le_bytes()  // 4 bytes LE
 || rules_version.as_bytes()
)
```

Generator initialization: `let mut rng = ChaCha12Rng::from_seed(derived_key);` (which initializes `stream = 0` and `word_pos = 0`, `read at source: https://docs.rs/crate/rand_chacha/0.10.0/source/src/chacha.rs, v0.10.0`). Each `next_u64()` call packs two consecutive little-endian `u32` block words as `(u64::from(hi) << 32) | u64::from(lo)` (`BlockRng::next_u64_from_u32`, `read at source: https://docs.rs/crate/rand_core/0.10.1/source/src/block.rs, v0.10.1`).

### 2.3 Unbiased integer range mapping (64-bit Lemire multiplication-rejection)

All dice rolls and weighted table selections map `rng.next_u64()` onto `[0, span)` (`span: NonZeroU64`) via Lemire's divisionless-fast-path unbiased integer multiplication algorithm (Daniel Lemire, *ACM TOMS* 45(1), 2019), using **zero floating-point operations**:

```rust
pub fn sample_u64(&mut self, span: NonZeroU64) -> u64 {
    let s: u64 = span.get();
    let x: u64 = self.next_u64_recorded();
    let mut m: u128 = u128::from(x) * u128::from(s);
    let mut low: u64 = m as u64; // m mod 2^64
    if low < s {
        // threshold = (2^64 - s) mod s == 2^64 mod s
        let threshold: u64 = s.wrapping_neg() % s;
        while low < threshold {
            let x_retry: u64 = self.next_u64_recorded();
            m = u128::from(x_retry) * u128::from(s);
            low = m as u64;
        }
    }
    (m >> 64) as u64
}
```

**Exactness & boundary invariants:**
- **Zero bias across all `NonZeroU64` (`1..=u64::MAX`):** Let $t = 2^{64} \bmod s$. Discarding the $t$ residue values `low < t` leaves $2^{64} - t$ accepted states per interval, an exact multiple of $s$, so every integer in `0..s` is returned with exact probability $1/s$.
- **Boundary check at `s = 1`:** `threshold = 1u64.wrapping_neg() % 1 = 0`; `while low < 0` never executes; `(m >> 64) as u64 == 0`; consumes exactly 1 `u64` draw (matching `1d1` consuming one RNG call in 2.x `src/engine/pipeline.ts:36`).
- **Boundary check at `s = u64::MAX` ($2^{64} - 1$):** `threshold = 1 % (2^64 - 1) = 1`. Only `x == 0` produces `low == 0 < 1` (rejected); the remaining $2^{64} - 1$ inputs `1..=u64::MAX` map 1-to-1 onto `0..(2^64 - 1)` with zero overflow.
- **Die face mapping:**
  - `DiceSides::Standard(n)` -> `1 + (sample_u64(NonZeroU64::from(n)) as i64)` in `1..=n`.
  - `DiceSides::Percentile` -> `1 + (sample_u64(NonZeroU64::new(100).unwrap()) as i64)` in `1..=100`.
  - `DiceSides::Fate` -> `(sample_u64(NonZeroU64::new(3).unwrap()) as i64) - 1` in `-1..=1`.

### 2.4 Byte-for-byte reproducibility across native and wasm targets

Bit-for-bit equality across `x86_64` (Windows/Linux), `aarch64` (macOS/ARM), `wasm32-unknown-unknown`, `wasm32-wasip1`, and the TypeScript port holds by construction:
1. **Zero floats on the execution path:** Neither `derive_roll_key`, `ChaCha12Rng`, `sample_u64`, `run_pipeline`, `evaluate`, nor `roll_table` executes a single `f32`/`f64` instruction (eliminating x87/SSE/WASM NaN-canonicalization and transcendental differences).
2. **Explicit endianness:** Every KDF integer uses `.to_le_bytes()`, ChaCha12 state words are defined over little-endian 32-bit words (`ppv-lite86` 0.2.21 `x86_64` SSE2 and `generic` scalar backend on `wasm32` emit identical streams; `ChaCha12Rng::from_seed([0u8; 32]).next_u64() == 0x53f955076a9af49b`, `read at source: https://docs.rs/crate/rand_chacha/0.10.0/source/src/lib.rs, v0.10.0`), and `u64` draws pack `lo | (hi << 32)` identically on all targets.
3. **Deterministic ordered collections:** `BTreeMap` and `BTreeSet` are used exclusively across `roll-core`; `usize` never appears in serialized receipts or RNG math.

**How cross-target reproducibility is tested:**
- CI builds and runs `roll-core` tests on `x86_64-pc-windows-msvc`, `x86_64-unknown-linux-gnu`, `aarch64-apple-darwin`, **and** `wasm32-wasip1` (executed via `wasmtime`), plus Vitest on Node >=22.
- Each target computes a running `SHA-256` over the canonical JSON bytes of 10,000 generated `RollReceipt`s (spanning dice modifiers, nested/chained tables, without-replacement multi-draws, and synthetic RNG words crafted with `low < s` and `low < threshold` to exercise Lemire's rejection loop) and asserts equality against the committed manifest digest in `fixtures/conformance/v3/MANIFEST.sha256`.

### 3.1 Exact receipt fields and JSON-safe encoding

JavaScript's `JSON.parse` coerces bare numbers to IEEE-754 `double`, silently corrupting integers outside $\pm(2^{53} - 1)$ (`9007199254740991`). - all `i64` and `u64` quantities (`turn`, `roll_index`, `Int64` seeds, `eligible_weight_total`, `step_weights`, `total`, die faces) as **canonical base-10 ASCII strings** (`"-42"`, `"0"`, `"18446744073709551615"`, no leading `+` or leading zeros);
- every `u64` word in `raw_draws` as a **fixed 16-character lowercase hex string** (`"53f955076a9af49b"`);
- every 32-byte digest (`Bytes32` seed, `collection_sha256`, `receipt_sha256`) as a **fixed 64-character lowercase hex string**.

### 3.2 Canonical JSON serialization

Receipts serialize to a deterministic **RFC 8785 (JSON Canonicalization Scheme, JCS)** subset:
1. **Zero floats:** Every receipt value is an object, array, boolean, `null`, small `u32` integer (`0..=10_000`), or UTF-8 string, completely avoiding IEEE-754 ECMAScript float formatting corner cases.
2. **Key ordering:** Object keys are sorted lexicographically by UTF-16 code units. All fixed receipt schema keys are lowercase ASCII (`a-z0-9_`), where UTF-8 byte `Ord` in `serde_json::Map` (backed by `BTreeMap<String, Value>` when `preserve_order` is disabled, `read at source: https://docs.rs/crate/serde_json/1.0.154/source/src/map.rs, v1.0.154`) equals UTF-16 code-unit order. User-defined keys (`context.variables`, `payloads`) are serialized via a small JCS key-sorting wrapper over `str::encode_utf16` so even non-ASCII keys above `U+FFFF` match `JSON.stringify` / RFC 8785 byte-for-byte.
3. **String escaping & whitespace:** Compact UTF-8 with zero whitespace between tokens and RFC 8259 minimal escapes with lowercase `\u00xx` hex for control characters (`0x00..=0x1F`), which `serde_json` 1.0.154 already emits via `static HEX_DIGITS: [u8; 16] = *b"0123456789abcdef"` (`read at source: https://docs.rs/crate/serde_json/1.0.154/source/src/ser.rs, v1.0.154`).
4. **Self-digest (`receipt_sha256`):** Computed as `SHA-256(canonical_json_without_receipt_sha256)` — i.e., canonical JSON of the receipt object with the `"receipt_sha256"` key omitted — then inserted as `"receipt_sha256"` in alphabetical key position.

### 3.3 Isolated third-party verification (`verify_receipt`)

A third party (another player at the *Merchant League* table, `roll verify`, or an independent 40-line Python/Node script) needs **only** the single `RollReceipt` JSON (plus the public `CompiledCollection` JSON if `spec.kind == "table"`) — never save files or prior turns:

1. **Schema & version check:** Confirm `schema_version == "roll.receipt.v1"` and `rules_version == address.rules_version == "roll.v3"`.
2. **Integrity digest check:** Strip `"receipt_sha256"`, serialize the remaining object to canonical JSON, compute `SHA-256`, and assert equality with `receipt.receipt_sha256`.
3. **Spec canonicality check:**
   - If `spec.kind == "expression"`: `let expr = parse(&spec.canonical_expression)?;` and assert `expr.to_canonical_string() == spec.canonical_expression`.
   - If `spec.kind == "table"`: assert `tables.is_some()` and `hex(tables.unwrap().sha256()) == spec.collection_sha256`.
4. **PRNG stream authenticity check:** Compute `key = derive_roll_key(&receipt.address)?`, initialize `ChaCha12Rng::from_seed(key)`, draw `receipt.raw_draws.len()` words via `next_u64()`, and assert exact element-by-element equality with `receipt.raw_draws`.
5. **Deterministic execution & exact draw exhaustion check:** Re-execute `expr` (or `roll_table` / `roll_table_multiple` under `spec.context`) against a bounded tape cursor over `receipt.raw_draws`:
   - Assert the tape neither underflows (missing draws) nor leaves unconsumed trailing words at termination (`cursor == receipt.raw_draws.len()`).
   - Assert recomputed `eligible_weight_total`, `step_weights`, and `result` equal the receipt's fields identically.

## 4. Grammar and AST

### 4.1 Fixing the 2.x lexer failures (`1d20cscf`, `4d6khsa`, `2d6rsa`)

**Root cause in 2.x:** `src/parser/lexer.ts:70-72` enforces an ASCII letter word-boundary check (`if (nextChar && nextChar >= "a" && nextChar <= "z") continue;`) inside a global pre-tokenizer (`DICE_CONTEXT_TOKENS` at `src/parser/lexer.ts:32-56`). Any modifier keyword immediately followed by another letter-initial modifier without an intervening digit — `1d20cscf`, `4d6khsa`, `2d6rsa` — fails keyword matching and throws `LexerError`. Worse, `buildExpression` (`src/engine/roller.ts:74-91`) strips whitespace (`"1d20cs cf"` $\to$ `"1d20cscf"`), breaking serializer round-tripping (`src/engine/roller.ts:188-190`).

**Roll 3.0 fix — modal scannerless recursive-descent parser:**
Eliminate the separate context-guessing `tokenize()` pass. The parser scans `&str` directly in two explicit syntactic modes:
1. **`ExprMode` (outside a dice term):** Skips ASCII space/tab (`' '`, `'\t'`), matches integer literals, `+`, `-`, `*`, `/`, `(`, `)`, and `[dD]` (entering `DiceMode`). Letters other than `[dD]` are immediately `RollError::Lex` with exact byte offset.
2. **`DiceMode` (immediately after `<count>?[dD]`):**
   - **Sides slot (parsed once):** Match `'%'` $\to$ `Percentile`, `['f' | 'F']` $\to$ `Fate`, or unsigned digits $\to$ `Standard(n)` (`1..=MAX_DIE_SIDES`). Because `'f'`/`'F'` is *only* tested in this sides slot, `cf` in the modifier loop can never collide with Fate dice.
   - **Modifier loop (zero word-boundary lookahead):** Repeatedly match the longest prefix at the current byte cursor from the ordered keyword table:
     `["min", "max", "kh", "kl", "dh", "dl", "ro", "cs", "cf", "sa", "sd", "!p", "!!", "!", "r"]`
     and immediately parse that modifier's argument (`required <int>` for `min`/`max`, `optional <u32>` for `kh`/`kl`/`dh`/`dl`, `optional <ComparePoint>` for `!`/`!!`/`!p`/`r`/`ro`/`cs`/`cf`, none for `sa`/`sd`).

**Unambiguous decodability proof without whitespace:**
Among the 15 modifier prefixes, only two pairs share a strict prefix: `("r", "ro")` and `("!", "!!", "!p")`.
- No modifier keyword begins with `'o'` or `'p'`. Therefore, bare `"r"` followed by any valid subsequent modifier (`r`, `min`, `max`, `kh`, `kl`, `dh`, `dl`, `cs`, `cf`, `sa`, `sd`, `!`, `!!`, `!p`) never begins with `"ro"`, and bare `"!"` followed by any valid non-explosion modifier never begins with `"!p"` or `"!!"`. (Multiple explosion modifiers on one dice group are forbidden; see Section 4.2.)
- Every other modifier keyword has fixed length 2 (`kh`, `kl`, `dh`, `dl`, `cs`, `cf`, `sa`, `sd`) or 3 followed by mandatory digits (`min`, `max`).
- Thus `1d20cscf` parses deterministically as `1d20` + `cs` + `cf`; `4d6khsa` parses as `4d6` + `kh(1)` + `sa`; `2d6rsa` parses as `2d6` + `r(=1)` + `sa`; and `parse(expr.to_canonical_string()) == Ok(expr)` holds for **every** constructible `Expr`.

### 4.2 Typed canonical stage slots and parse-time validation

Instead of `modifiers: DiceModifier[]` (`src/parser/ast.ts:42`), which permitted engine and analyzer helpers to inspect modifiers in inconsistent orders (`src/engine/pipeline.ts:131-147` vs `256a911` `src/analyze/distribution.ts:256-290`), `parse()` populates the typed `DiceSpec` stage slots (Section 1.2) and validates all static invariants before returning `Ok(Expr)`:

1. **Expression byte cap:** `input.len() <= MAX_EXPRESSION_BYTES` (`1_000` bytes, matching `src/parser/parser.ts:24`). Nesting is capped too: parentheses and unary operators deeper than a stated `MAX_NESTING_DEPTH` are refused with a structured `RollError` (with its byte offset), set low enough that parsing, evaluation and analysis cannot overflow the stack in a debug build. Without it, about 450 nested parentheses (under the byte cap) overflow the stack in release.
2. **Per-group & AST-wide dice budgets:**
   - Every `DiceSpec.count` must be `1..=MAX_DICE_PER_GROUP` (`10_000`; **`0d6` is rejected** at parse time, closing `src/parser/parser.ts:153,180`).
   - Die sides must be `1..=MAX_DIE_SIDES` (`1_000_000`).
   - **AST-wide budget:** As `parse` constructs `DiceSpec` nodes, it accumulates `total_dice: u64` across the entire AST (including both branches of `+`, `-`, `*`, `/`) and rejects any expression with `total_dice > MAX_TOTAL_DICE_PER_EXPR` (`10_000`) via `RollError::DiceBudgetExceeded`, closing the `>100 × 10000d6` multi-group allocation gap in `src/parser/parser.ts:180`.
3. **Canonical slot uniqueness & `min <= max`:**
   - `reroll_unlimited: Vec<ComparePoint>` (`r`, bare `r` resolved to `=1`) and `reroll_once: Vec<ComparePoint>` (`ro`, bare `ro` resolved to `=1`). Multiple `r`/`ro` modifiers are allowed and preserved in stage order (`all r` in syntax order, then `all ro` in syntax order, matching `stageReroll` at `src/engine/pipeline.ts:98-122` and `singleDieWithReroll` at `src/analyze/distribution.ts:233-301`).
   - `clamp: Option<ClampBounds>`: At most one `min` and at most one `max` per dice group (duplicate `min` or duplicate `max` throws `RollError::Parse`). When both `min` and `max` are present and `min > max` (e.g. `1d6min5max2` or `1d6max2min5`), `parse` immediately returns `Err(RollError::InvalidClampBounds { min, max, byte_offset })`. Because `min <= max` is guaranteed, `v.max(min).min(max) == v.min(max).max(min)` — clamping order can never drift.
   - `explode: Option<ExplosionRule>`: At most **one** explosion modifier (`!`, `!!`, or `!p`) per dice group (multiple explosions throw `RollError::Parse`, matching PR #11 `explosionDistribution` returning `null` on `explodeMods.length !== 1` at `src/analyze/distribution.ts:514`). Default compare point `>= max_face` is resolved at parse time. **Exploding Fate dice (`4dF!`, `4dF!!`, `4dF!p`) are rejected at parse time** rather than accepted as silent no-ops (`src/engine/pipeline.ts:158-159`).
   - `keep_drop: Vec<KeepDropOp>`: Bare `kh`/`kl`/`dh`/`dl` resolve to `1` at parse time (`4d6kh` $\to$ `KeepHighest(1)`). `0` (`4d6kh0` keeps 0 dice; `4d6dl0` drops 0 dice) is allowed as non-negative `u32`.
   - `mode: ResultMode`:
     - `cs<ComparePoint>` and/or `cf<ComparePoint>` populate `ResultMode::Pool { cs, cf }`.
     - Bare `cs` and/or bare `cf` (with no compare point, e.g. `1d20cs`, `1d20cf`, `1d20cscf`) populate `ResultMode::Sum { crit_success_max, crit_failure_min }`, marking kept dice equal to `max_face` (`+1` on `dF`) as `CritKind::Success` and kept dice equal to `min_face` (`1`, or `-1` on `dF`) as `CritKind::Failure` without switching out of `Sum` mode (fixing the dead no-op in `src/engine/pipeline.ts:320-330`).
     - Mixing bare `cs`/`cf` with `cs<ComparePoint>`/`cf<ComparePoint>` in the same dice group is rejected at parse time with an explicit message distinguishing sum-mode critical marking (`1d20cscf`) from pool success counting (`8d6cs>=5cf<=1`).
   - `sort: Option<SortOrder>`: At most one of `sa` or `sd` (both together throws `RollError::Parse`). Affects CLI/UI display formatting only; `GroupOutcome.dice` in receipts always preserves exact draw order.
4. **Canonical string serialization (`Expr::to_canonical_string`):**
   - Always emits explicit count (`d20` $\to$ `1d20`), uppercase `F` (`4df` $\to$ `4dF`), and modifiers in fixed pipeline stage order:
     `reroll_unlimited` (`r<op><v>`) $\to$ `reroll_once` (`ro<op><v>`) $\to$ `min<v>` $\to$ `max<v>` $\to$ `explode` (`!`/`!!`/`!p` + `<op><v>`) $\to$ `keep_drop` (`kh<n>`/`kl<n>`/`dh<n>`/`dl<n>`) $\to$ `mode` (`cs...`/`cf...`) $\to$ `sort` (`sa`/`sd`), with minimal parentheses preserving precedence.

### 4.3 Checked `i64` arithmetic and explicit division semantics

- All integer literals, compare-point thresholds (`min`/`max`/`r`/`!` values may also take optional leading `-` so Fate expressions like `4dFr=-1` or `4dFmin0` are expressible!), die totals, and binary operations execute in **checked signed 64-bit integer arithmetic (`i64`)**:
  - `checked_add`, `checked_sub`, `checked_mul`, `checked_neg` return `Err(RollError::ArithmeticOverflow)` on overflow (never wrapping or promoting to `f64`).
- **Explicit division semantics — integer floor division toward $-\infty$ (`DivFloor`):**
  - Roll 2.x uses `Math.floor(left / right)` (`src/engine/roller.ts:167`, `src/analyze/distribution.ts:654,676`). Note that Rust's `/` truncates toward `0` (`-7 / 2 == -3`) and Rust's `i64::div_euclid` rounds toward $-\infty$ only for positive divisors (`(-7i64).div_euclid(-2) == 4`, whereas $\lfloor -7 / -2 \rfloor = \lfloor 3.5 \rfloor = 3$, and `(7i64).div_euclid(-2) == -3`, whereas $\lfloor 7 / -2 \rfloor = \lfloor -3.5 \rfloor = -4$).
  - Roll 3.0 specifies **exact mathematical floor division $\lfloor a / b \rfloor$ toward $-\infty$** on `i64` (`checked_div_floor`):
    ```rust
    pub fn checked_div_floor(a: i64, b: i64) -> Result<i64, RollError> {
        if b == 0 {
            return Err(RollError::DivisionByZero);
        }
        let q = a.checked_div(b).ok_or(RollError::ArithmeticOverflow)?; // catches i64::MIN / -1
        let r = a % b;
        if r != 0 && (r < 0) != (b < 0) {
            q.checked_sub(1).ok_or(RollError::ArithmeticOverflow)
        } else {
            Ok(q)
        }
    }
    ```
    This agrees 100% with 2.x `Math.floor(a / b)` across all safe integers (including D&D `(score - 10) / 2` negative ability modifiers and negative divisors) while remaining exact across the full `i64` range with zero `f64` precision loss.

## 5. The exact analyzer

PR #11 (`719174717254762e2c1f235fb73792a46fa55995`) is the normative reference for `"exact"`: exact means **exact for the bounded engine pipeline as built**, including its loop caps (`MAX_EXPLOSIONS = 100`, `MAX_REROLLS = 100`), never an unlabelled approximation.

### 5.1 Single-die PMF composition in pipeline stage order

For any `DiceSpec`, `roll-core` builds the exact single-die PMF by composing Stages 1 $\to$ 2 $\to$ 3 (and Stage 4 when applicable) in the exact order of `runPipeline` (`src/engine/pipeline.ts:372-404`):

1. **Stage 1 (Base uniform die):** `Distribution` over `-1..=1` at $1/3$ each (`Fate`) or `1..=s` at $1/s$ each (`Standard(s)` / `Percentile`).
2. **Stage 2 (Sequential capped rerolls + reroll-once):**
   - For each `cp` in `spec.reroll_unlimited`: partition the die's $s$ base faces into $M_{\text{match}}$ ($m = |M_{\text{match}}|$) and $M_{\text{keep}}$ ($s - m$ faces). Let $p_{\text{match}} = \sum_{f \in M_{\text{match}}} D(f)$. If $m > 0$ and $p_{\text{match}} > 0$:
     - Record `caps.max_rerolls = Some(MAX_REROLLS)` (`100`, matching `src/analyze/distribution.ts:265`).
     - If $m == s$ (every face matches, e.g. `1d6r>=1`): in `stageReroll` (`src/engine/pipeline.ts:104-108`), all 100 rerolls match and the 100th fresh uniform roll stands, so $D'(f) = 1/s$ for every $f \in M_{\text{match}}$ with `caps.max_rerolls = Some(100)`. *(Note: PR #11 `src/analyze/distribution.ts:250-252` returned `null` here only to preserve a 2.1.0 MC test at `tests/analyze-correctness.test.ts:197-228`; in 3.0, surfacing `caps.max_rerolls = Some(100)` makes `1d6r>=1` closed-form exact too.)*
     - If $0 < m < s$: let $q = m / s$ and $q_{\text{cap}} = q^{100}$. Each $f \in M_{\text{keep}}$ receives $D'(f) = D(f) + p_{\text{match}}(1 - q_{\text{cap}}) / (s - m)$, and each $f \in M_{\text{match}}$ remains **reachable** in the support with residual probability $D'(f) = (p_{\text{match}} \cdot q_{\text{cap}}) / m$ (even if `f64` underflows to `0.0`; see Section 5.4).
   - For each `cp` in `spec.reroll_once`: let $p_{\text{match}} = \sum_{f \in M_{\text{match}}} D(f)$; set $D'(f) = (\text{if } f \in M_{\text{match}} \text{ then } 0 \text{ else } D(f)) + p_{\text{match}} / s$.
3. **Stage 3 (Clamp):** If `Some(ClampBounds { min, max })`, sweep all mass at $v < \text{min}$ onto $\text{min}$ and all mass at $v > \text{max}$ onto $\text{max}$, giving $D_{\text{pre}}$.
4. **Stage 4 (Explosion depth expansion up to `MAX_EXPLOSIONS = 100`):**
   - Mirrors `explosionDistribution` (`src/analyze/distribution.ts:503-590`): depth `0` draws from $D_{\text{pre}}$ (post-reroll, post-clamp), while bonus rolls at depths `1..=100` draw uniformly from raw faces `1..=s` (`stageExplode` calls `rollSingleDie` directly at `src/engine/pipeline.ts:175,191,212`).
   - For `Penetrate` (`!p`), depths `>= 1` add `max(1, raw_face - 1)` while testing `matches_compare(raw_face, threshold)` on the **unadjusted** `raw_face` (`src/engine/pipeline.ts:213-215`, `src/analyze/distribution.ts:558-566`).
   - Whenever `matches_compare(raw_face, threshold)` holds at `depth == MAX_EXPLOSIONS`, the chain terminates and sets `caps.max_explosions = Some(MAX_EXPLOSIONS)` (`100`, `src/analyze/distribution.ts:567-570`).
   - **Upgrade over #11 for exploding pools (`8d6!cs>=5`, `8d6!pcs>=5`) and compounding keep/drop (`4d6!!kh3`):**
     - When `mode` is `Pool { cs, cf }` and `keep_drop.is_empty()`, each initial die's explosion chain contributes $\sum_{d=0}^{K} c(v_d) \in [-101, +101]$ independently ($c(v) \in \{-1, 0, +1\}$). Running the same 100-depth chain expansion accumulating `acc_net + c(effective_face)` (at most 203 states per depth) produces the **exact** single-chain net-success PMF, which convolves $N$ times (`8d6!cs>=5` is now `"exact"`).
     - When `explode` is `Compound` (`!!`), bonus rolls sum into the **same** die (`src/engine/pipeline.ts:192`), leaving exactly $N$ i.i.d. dice drawn from $D_{\text{exploded}}$. Thus `4d6!!kh3` feeds directly into the Order-Statistic DP below as `"exact"`.
     - Only `Standard` (`!`) or `Penetrate` (`!p`) combined with non-empty `keep_drop` (e.g. `4d6!kh3`, which spawns variable-size multisets of individual dice before `stageKeepDrop`) abandons `try_exact` to `AnalysisMethod::MonteCarlo { samples: 100_000 }`, matching PR #11 (`src/analyze/distribution.ts:803-805`).

### 5.2 Order-statistic dynamic programming for `keep/drop`

Roll 2.x's `enumerateKeepDrop` (`src/analyze/distribution.ts:424-490`) enumerates $M^N$ outcomes ($20^{10} \approx 10^{13}$ on `10d20kh3`), forcing simple keep/drop rolls into Monte Carlo. Roll 3.0 replaces it with exact **division-free multinomial order-statistic DP**:

1. **Rank-interval reduction:** Any sequence of `KeepDropOp` modifiers on $N$ sorted dice $X_{(0)} \le \dots \le X_{(N-1)}$ reduces deterministically to a single half-open rank interval $[L, R) \subseteq [0, N)$:
   - Initialize $(L, R) = (0, N)$.
   - `KeepHighest(k)` $\implies L \leftarrow R - \min(k, R - L)$.
   - `KeepLowest(k)` $\implies R \leftarrow L + \min(k, R - L)$.
   - `DropHighest(k)` $\implies R \leftarrow R - \min(k, R - L)$.
   - `DropLowest(k)` $\implies L \leftarrow L + \min(k, R - L)$.
   - If $L == R$, return the point distribution `{(0, 1.0)}` immediately.
2. **Division-free multinomial DP recurrence:**
   Let $(v_0, p_0), \dots, (v_{M-1}, p_{M-1})$ be the ascending single-die PMF (using $D_{\text{exploded}}$ if `Compound`, else $D_{\text{pre}}$), and let $\text{val}(v_i) = v_i$ in `Sum` mode or $c(v_i) \in \{-1, 0, +1\}$ in `Pool` mode.
   Maintain `dp[j]` ($0 \le j \le N$), mapping `partial_sum: i64 -> prob: f64` after assigning $j$ dice among $\{v_0, \dots, v_{i-1}\}$, initialized at `dp[0] = {(0, 1.0)}`.
   For each face $i = 0 \dots M - 1$, build `next_dp`: for each $j \in 0..=N$ with non-empty `dp[j]` and each count $c \in 0..=(N - j)$ placed on $v_i$:
   - Transition factor: $w(j, c) = \binom{j + c}{c} p_i^c$. Because $\prod_{i=0}^{M-1} \binom{j_i + c_i}{c_i} = \frac{N!}{c_0! \cdots c_{M-1}!}$ telescopes with **zero division**, tiny `MAX_REROLLS` residuals ($p_i = 6^{-101}$) never divide by near-zero tail sums.
   - Kept overlap at rank slice $[j, j + c) \cap [L, R)$:
     $$k_{\text{kept}}(j, c) = \max\bigl(0,\ \min(j + c, R) - \max(j, L)\bigr)$$
   - Every `(s, p)` in `dp[j]` transitions to `(s + k_kept(j, c) * val(v_i), p * w(j, c))` in `next_dp[j + c]`.
   - At $i = M$, `dp[N]` is the exact distribution of the `DiceSpec`.
3. **Cost guard:** Before each face step $i$, accumulate total inner transitions $\sum_{j=0}^{N} |\text{dp}[j]| \cdot (N - j + 1)$. If accumulated work or state count exceeds `MAX_EXACT_STATES` (`10_000_000`), abort `try_exact` with internal `ExactTooLarge` and fall back to Monte Carlo. For `10d20kh3` ($N = 10, M = 20$, sum width $\le 58$), total transitions are $\le 20 \times 66 \times 58 = 76,560$ ($\approx 1.3 \times 10^8\times$ fewer than $20^{10}$).

### 5.3 Honest `AnalysisMethod`, `ModelledCaps`, budgets, and algebra

- **Budgets:** `MAX_ANALYZE_DICE = 1_000` across the whole AST (`RollError::AnalysisBudgetExceeded` before any work, matching `src/analyze/distribution.ts:152,733-741`), and one exact-analysis budget per `analyze` call across the whole AST: at most `MAX_EXACT_STATES = 10_000_000` cumulative transitions and at most `MAX_EXACT_LIVE_STATES = 2_000_000` live retained states, each charged **before** the allocation or loop it pays for (the weights are documented in `crates/roll-core/src/analyze.rs`). When the budget runs out, analysis falls back to Monte Carlo. Divisors are analyzed first, under a budget of their own (§5.4). `compare` analyzes each side under its own budget, plus one for the margin.
- **Method & caps tag (`AnalysisMethod`):**
  - `AnalysisMethod::Exact { caps: None }` when closed-form exact with no loop cap exercised (`2d6`, `4d6ro=1kh3`).
  - `AnalysisMethod::Exact { caps: Some(ModelledCaps { max_explosions, max_rerolls }) }` whenever an exact distribution exercises `MAX_EXPLOSIONS = 100` and/or `MAX_REROLLS = 100` (populated only for caps actually reached, matching `src/analyze/distribution.ts:265,568-570,757-761`).
  - `AnalysisMethod::MonteCarlo { samples }` when `try_exact` returns `None` or hits `ExactTooLarge`, sampled from a single continuous `ChaCha12Rng::from_seed(*b"roll.v3.montecarlo.default.seed!")` stream (`src/analyze/montecarlo.ts:31-37`). `samples` is the number of completed trials: at most `DEFAULT_MONTE_CARLO_SAMPLES = 100_000`, and fewer when the work ceiling `MAX_MC_WORK` is reached first. The ceiling counts RNG draws, the per-die `r`/`ro` scans and keep/drop sort work, so every input under the 1,000-byte expression limit analyzes in under 1 second in a release build. The tag always reports the real count, and each probability is a count divided by `samples`.
- **Binary algebra & `compare`:**
  - `+`, `-`, unary `-`: exact shift/scale/convolution (using binary exponentiation by squaring in `convolve_n` to cut $N$-fold convolution steps from $N$ to $\lceil \log_2 N \rceil$).
  - `*`: exact `scale_distribution` when either side is a point mass, **plus** exact `multiply_distributions(left, right)` when `left.len() * right.len() <= MAX_EXACT_STATES` (upgrading `(1d6)*(1d6)` from 2.x's MC fallback at `src/analyze/distribution.ts:942` to `"exact"`).
  - `compare(left, right)`: wraps `convolve(left, negate(right))` inside the `ExactTooLarge` handler — if `left.len() * right.len() > MAX_EXACT_STATES` (e.g. `compare("100d100", "100d100")`, $9901^2 > 10^7$), `compare` computes exact `p_left_greater`, `p_equal`, `p_right_greater` in $O(|A| + |B|)$ via a **two-pointer linear scan** over the sorted supports of $A$ and $B$ (setting `margin: None`, `method: Exact`) instead of crashing with uncaught `ExactTooLargeError` (`src/analyze/distribution.ts:996-1012` / `src/bridge/handler.ts:295`).

### 5.4 Exact reachability and the divide-by-zero contract

In PR #11 (`src/analyze/distribution.ts:270,403,561,677`), JS products that underflow `f64` to `0.0` (e.g. $(20^{-101})^3 \approx 6.1 \times 10^{-395} < 5 \times 10^{-324}$) were clamped to `Number.MIN_VALUE` so `(right.get(0) ?? 0) > 0` stayed true on `1d6/(5d20r=1-5)`. In Roll 3.0, `Distribution` stores every **reachable** integer outcome as an entry `(value, prob_f64)` in its sorted `Vec<(i64, f64)>`: an entry is inserted iff it has $\ge 1$ valid execution path with non-zero rational probability, **even if `pa * pb` underflows IEEE-754 `f64` to `0.0`**, without fabricating `5e-324` mass. Thus `dist.is_reachable(0)` (`entries.binary_search_by_key(&0, |&(v, _)| v).is_ok()`) is **mathematically exact** at arbitrary depth.

**Divide-by-zero contract (`BinaryOp::DivFloor`, matching PR #11 `src/analyze/distribution.ts:705-718, 831-871`):**
1. Before the main pass, analyze every `DivFloor` divisor subtree, smallest first, under a budget reserved for divisors and separate from the main budget (§5.3).
2. If a divisor is exact under that budget and `is_reachable(0)` is `true` (i.e. true $P(\text{divisor} = 0) > 0$), **return `Err(RollError::DivisionByZero)`**, however large the other operands are and in whatever order siblings are visited (e.g. `500d1000/(5d20-5)` and `(1d999990*0+1d999990*0+1d999990*0+1d999990*0+1d999899*0+1/1)+1d6/(5d20-5)` both error deterministically).
3. Isolate `ExactTooLarge` on `left` and `right` separately so any nested `RollError::DivisionByZero` inside `left` still propagates as `Err(RollError::DivisionByZero)` when `right` exceeds `MAX_EXACT_STATES` (e.g. `(1d6/(5d20-5))+500d1000`).
4. If a divisor is non-exact (too large for the divisor budget, or `try_exact` returns `None`, e.g. `1d6/(5d20!kh4-4)`), fall back to `monte_carlo_distribution` (up to `100_000` `evaluate` trials, fewer when `MAX_MC_WORK` is reached, §5.3): if any trial rolls a `0` divisor (`1d6/(4d6!kh3-12)`), `evaluate` returns `Err(RollError::DivisionByZero)`; if a rare zero outcome is not hit, the report is tagged `AnalysisMethod::MonteCarlo { samples }` with the real trial count, **never** `Exact`. A rare zero can be missed only when its divisor is too large to analyze exactly.
5. **Error precedence.** When more than one error is reachable (e.g. `(1d6/(1d2-1))+(9223372036854775807+1d2)` can raise both `DivisionByZero` and `ArithmeticOverflow`), a reachable zero from an exact divisor wins, because divisors are checked first. The TypeScript port reproduces this rule. A single `evaluate` raises whichever error its draw order reaches first.

## 6. Tables

### 6.1 Schema v3.0: `NonZeroU64` weights, `EntryBody` enum, and `rollExpression` decision

**Decision on `GameTable.rollExpression` (`src/tables/schema.ts:88`): REMOVED.**
- In 2.x, `rollExpression` was a dead schema field never read in `engine.ts`, `validate.ts`, or `analyze.ts`.
- Implementing a second dice-band lookup model alongside weighted selection creates unresolvable conflicts with Roll 3.0's core contracts: overlapping or gapped bands fail at runtime under context filtering, weighted sampling without replacement (`allow_duplicates: false`) degrades back to rejection-sampling loops, and `RollReceipt.eligible_weight_total` (Section 3) becomes ill-defined.
- Any finite bell-curve or percentile table is **isomorphic** to exact integer weights: e.g., a `2d6` encounter table (`2..=12`) uses exact integer weights `[1, 2, 3, 4, 5, 6, 5, 4, 3, 2, 1]` (`eligible_weight_total = 36`), and a `d100` band table (`01–65`, `66–90`, `91–100`) uses weights `[65, 25, 10]` (`eligible_weight_total = 100`). Keeping **one** selection primitive (`NonZeroU64` prefix sum) gives uniform receipts, gap-free context filtering, and exact without-replacement draws everywhere. (`roll-core` provides an authoring helper `weights_from_pmf(expr: &Expr) -> Result<BTreeMap<i64, u64>, RollError>` for designers generating bell-curve JSON tables `[Guess]`.)

**Core schema types (`#[serde(deny_unknown_fields)]`):**

### 6.2 Compile-on-load validation (`CompiledCollection::compile`)

Raw JSON is **never** passed directly to `roll_table` or `analyze_table` (closing the Bridge/MCP unvalidated-load bugs at `src/bridge/handler.ts:307,515-535` and `src/mcp/server.ts:136-160`). `CompiledCollection::compile` runs all checks upfront and returns **all** accumulated `TableCompileError`s:
1. `version == "3.0"`, non-empty unique `table.id` across the collection, non-empty `entries` per table, non-empty unique `entry.id` within each table.
2. **Checked `u64` weight sum:** Sum of `entry.weight.get()` across all entries in each table must not overflow `u64::MAX` (`WeightSumOverflow`), guaranteeing no subset of eligible entries can ever overflow `u64` at runtime.
3. **Reference integrity:** Every `Nested { table }` and every element of `chain` must exist in the collection (`UnknownTableRef`, `UnknownChainRef`).
4. **Complete multi-cycle DAG check & depth bound:** Three-color DFS / Tarjan's SCC over the union of `Nested` and `chain` edges **without early exit** (fixing `src/tables/validate.ts:114,117` which aborted on the first cycle per root), reporting every elementary cycle, and computing topological order plus maximum DAG path depth (`<= MAX_TABLE_DAG_DEPTH = 16`, returning `DagDepthExceeded` otherwise).
5. **Pre-parsed `Expr` ASTs:** Every `quantity` and `payloads[k]` string is parsed via `parse(expr)` into a compiled `Expr` (catching syntax errors, `min > max`, and dice budgets on load, and eliminating repeated runtime `parse()` calls in `src/tables/engine.ts:200,208,217`). Furthermore, `analyze` checks that no compiled entry expression has an exact divisor with $P(0) > 0$.
6. **Condition validation:** Rejects empty variable names or empty `TextIn` sets.
7. Computes `collection_sha256: [u8; 32]` over the canonical JSON representation of the collection.

### 6.3 True weighted sampling without replacement (`roll_table_multiple`)

Replaces 2.x's `(target + 1) * 8` rejection-sampling loop (`src/tables/engine.ts:110-120`), which under-returned on skewed weight tables and wasted variable RNG draws:
- If `table.allow_duplicates == true`: execute `count` sequential draws against the full eligible slice; each draw records `eligible_weight_total` in `step_weights` and resolves nested/chain tables in order.
- If `table.allow_duplicates == false`:
  1. Filter `table.entries` against `context` $\to$ `pool: Vec<&CompiledEntry>`.
  2. If `pool.is_empty()`, return `Err(RollError::NoEligibleEntries)`.
  3. If `count.get() as usize > pool.len()`:
     - under `UniqueExhaustionPolicy::Error` (default), return `Err(RollError::InsufficientUniqueEntries { table_id, requested: count.get(), eligible: pool.len() })` before drawing any random numbers;
     - under `UniqueExhaustionPolicy::Truncate`, set `target = pool.len()`.
  4. Maintain `remaining_weight: u64 = pool.iter().map(|e| e.weight.get()).sum()`. For step `0..target`:
     - Push `remaining_weight` to `receipt.step_weights`.
     - Draw `ticket = rng.sample_u64(NonZeroU64::new(remaining_weight).unwrap())` in `0..remaining_weight`.
     - Scan `pool` accumulating `cum_weight += entry.weight.get()`; select the first index `idx` where `ticket < cum_weight`.
     - Remove `pool.remove(idx)` (preserving deterministic relative order of remaining entries!), set `remaining_weight -= chosen.weight.get()`, and resolve `chosen` (evaluating `quantity`, sorted `payloads`, or recursing into `Nested { table }`, then evaluating `chain` tables in array order).
  - **Guarantees:** Exact `target` unique top-level entries every time, $O(\text{target} \times |\text{pool}|)$ work, zero retry loops, and exact reproducibility in receipts.

 RPG-specific `minLevel`/`maxLevel`/`rarity`/`triggerNat` (`src/tables/schema.ts:75-77, 98, 104`) are replaced by general typed conditions suited to both RPGs (`variables["level"] = Int(5)`) and *Merchant League*:

### 6.5 Static DAG `analyze_table` parity with `roll_table`

`analyze_table` traverses the validated acyclic `CompiledCollection` **bottom-up in reverse topological order with memoization per `table_id`**:
- Expands `Nested` references to the **full DAG depth** (removing `MAX_NESTED_DEPTH = 1` at `src/tables/analyze.ts:95`) in $O(|V| + |E|)$ table evaluations rather than exponential path re-traversal on diamond graphs.
- If an eligible `Nested` parent entry points to a child table that has **zero** eligible entries under `context`, `analyze_table` returns `Err(RollError::NoEligibleEntries { table_id: child_id })` — matching `roll_table` instead of silently dropping parent probability mass (`src/tables/analyze.ts:160-199`).
- Applies `.max(1)` clamping to `quantity` distributions so `analyze_table` matches `resolveEntry` (`src/tables/engine.ts:201`), and includes analyzed `chain` outcomes alongside each entry.

## 7. The TypeScript surface

### 7.1 Wrapper vs verified pure TypeScript port decision

`@mcptoolshop/roll` remains the official npm package (`"type": "module"`, `"engines": { "node": ">=22" }`, zero runtime `"dependencies"`). Three architectures were evaluated against the brief's criteria and Section 1's `#![forbid(unsafe_code)]` mandate:

| Criterion | N-API native addon (`napi-rs`) | Thin WASM wrapper (`wasm-bindgen`) | **Pure TS port verified against `roll-core` fixtures** |
|---|---|---|---|
| **Bundle / publish size** | Multi-MB per OS/arch `.node` binaries | ~120–250 KB monolithic `.wasm` (+33% if base64-inlined); non-tree-shakeable | **Smallest:** ~2,600 LoC across core modules in `7191747` (`~95 KB` unminified `.ts`), tree-shakeable ESM `.js` + `.d.ts` |
| **Install friction & native builds** | High risk: unsupported platforms fall back to local Rust/`node-gyp` builds | Zero for npm consumers if prebuilt `.wasm` is checked into `dist/` | **Zero:** plain JS files in `dist/`; zero `postinstall` scripts |
| **Windows compatibility** | Corporate Windows Defender / AppLocker policies frequently block unsigned `.node` DLLs in `node_modules` | Contributor/CI friction keeping `wasm-bindgen-cli` pinned to `wasm-bindgen` `0.2.130` | **Seamless:** builds with `tsc` (`package.json:34`) identically on Windows, Linux, and macOS |
| **Sync ESM & Browser / VTT support** | Fails completely in browsers and edge workers | **Breaks sync ESM in browsers:** V8 throws `RangeError` on synchronous `new WebAssembly.Module` > 4 KB on the main thread, forcing async `await init()` or `node:fs` `readFileSync` | **100% synchronous** in Node >=22, browsers, Vite, and Astro (`site/`) with zero bundler plugins |
| **Section 1 `no unsafe` rule** | Macro FFI emits `unsafe` | **Violates `forbid(unsafe_code)`:** `wasm-bindgen-macro-support` `0.2.130` `src/codegen.rs` emits `unsafe fn` and `unsafe {}` blocks into the crate (`read at source: https://docs.rs/crate/wasm-bindgen-macro-support/0.2.130/source/src/codegen.rs, v0.2.130`) | **100% compliant:** zero FFI glue crates in the Rust workspace |
| **Semantic drift risk** | Low | Low | Medium if untested; **eliminated** via `roll-core`-generated CI conformance fixtures (Section 9) |

**Decision: Ship `@mcptoolshop/roll` 3.0.0 as a zero-dependency pure TypeScript port verified in CI against `roll-core`'s generated conformance fixture set.**
- **Why porting the 3.0 primitives to pure TS is tractable and exact:** ChaCha12 (`16 × u32` ARX words via `Math.imul` / `>>>`) and SHA-256 (`64`-round `u32` compression, cross-checked against `node:crypto` in tests) are ~120 lines of portable 32-bit JS together; `i64`, `u64`, and `u128` Lemire math (`(BigInt(x) * BigInt(s)) >> 64n`) run natively on ECMAScript `BigInt` with zero float rounding; and canonical JSON serialization uses UTF-16 code-unit key sorting (`a < b ? -1 : a > b ? 1 : 0`), which is native JS string comparison.
- **JS numeric boundary contract:** `RollResult.total` is returned as `number` when `Number.isSafeInteger` (`|total| <= 2^53 - 1`) and always accompanied by `totalBigInt: bigint` (with `RollReceipt` fields always serialized as exact canonical strings). Seeds accept `bigint | number` (rejecting non-integers, `NaN`, `Infinity`, and unsafe `number`s) or `{ bytes32: Uint8Array | string }`.
- **Subpath export fix (`package.json:18-25`):** `"."` exports `./dist/index.js` + `./dist/index.d.ts`, and `"./tables"` exports a unified `./dist/tables/index.js` + `./dist/tables/index.d.ts` re-exporting **both** runtime functions (`compileTables`, `rollTable`, `rollTableMultiple`, `analyzeTable`) and TypeScript types. `"./bridge"` is removed.

### 7.2 Fate of `roll-bridge` and `roll-mcp`

- **`roll-bridge` (`src/bridge/*`, `package.json:10,22-25`): GOES (removed in 3.0.0, not ported to Rust).**
  - *Justification:* `roll-bridge` existed solely as an IPC shim for non-JS game runtimes to hold stateful RNG and table sessions inside a Node child process (`src/bridge/handler.ts:48-49`). The studio's Rust trading game links `roll-core` directly in-process with stateless `RollAddress` receipts, and external scripts that want one-shot JSON can invoke `roll --json` without running an HTTP/JSON-RPC server.
- **`roll-mcp` (`src/mcp/*`, `package.json:11`): STAYS in TypeScript inside `@mcptoolshop/roll`, with optional `crates/roll-mcp` in Rust.**
  - *Justification:* External MCP users launch `@mcptoolshop/roll` via `npx -y -p @mcptoolshop/roll roll-mcp` across Windows, macOS, and Linux; moving MCP *exclusively* to Rust would reintroduce prebuilt native binary distribution into npm. Keeping the ~400-line zero-dependency stdio MCP server in `@mcptoolshop/roll` preserves zero-friction `npx` installation, updated in 3.0 to:
    1. add `seed` / `address` and `include_receipt` to **both** `roll_dice` and `roll_table` (fixing `src/mcp/tools.ts:115-140`);
    2. add `target_for` (`atLeast` break-even solver) alongside `at_most_for` on `analyze_dice` (fixing `src/mcp/tools.ts:41-70`);
    3. compile collections via `compileTables` on every table tool call and dispatch `count > 1` through `rollTableMultiple` (fixing `src/mcp/server.ts:136-160, 306-317`);
    4. add a `verify_receipt` tool and enforce a `times * total_base_dice <= 1_000_000` product guard on `roll_dice` (fixing `src/mcp/server.ts:221-228`).
  - In parallel, `crates/roll-mcp` (~200 LoC over `roll-core` + `serde_json`, zero extra crates) is included as an optional Cargo binary for local Rust-only studio environments, tested against the exact same JSON-RPC fixture file as TS `roll-mcp`.

## 8. Migration from 2.x

### 8.1 Complete list of breaking changes (2.1.2 $\to$ 3.0.0)

1. **Seeded PRNG outputs change everywhere:** `mulberry32` (`seed | 0` + `f64` scaling, `src/engine/random.ts:11-19`) is replaced by SHA-256 `RollAddress` KDF + `ChaCha12Rng` + 64-bit Lemire rejection sampling. Passing `NaN`, `Infinity`, floats (`1.5`), or unsafe JS `number`s (`> Number.MAX_SAFE_INTEGER` without `BigInt`) as a seed now throws `RollError` instead of silently coercing via `| 0`.
2. **Richer roll result & trace shape:** `DieResult.rerolledFrom?: number` (`src/engine/roller.ts:10`) is replaced by `DieTrace` (`initialFace`, `rerolls: number[]`, `clampedTo?: number`, `explosions: number[]`, `finalValue`, `kept`, `critical?`, `poolDelta?`), and `RollResult` adds `canonicalExpression` and `totalBigInt` (plus `receipt` on addressed/seeded calls).
3. **Grammar & parse-time rejections:**
   - Now rejected at parse time: `0d6`, `min > max` (`1d6min5max2`), duplicate singleton modifiers (`1d6min2min3`, `1d6!>5!>4`, `4d6sasd`), exploding Fate dice (`4dF!`), mixed bare `cs` + pool `cs>=N`, and expressions with `> 10,000` total dice across all groups.
   - Changed runtime semantics (bug fixes): bare `1d20cs`/`1d20cf`/`1d20cscf` marks natural max/min faces in `Sum` mode; `1d20cscf` and `4d6khsa` now parse; `1d6r>=1`, `10d20kh3`, `4d6!!kh3`, `8d6!cs>=5`, and `(1d6)*(1d6)` now return `method: "exact"` instead of `"monte-carlo"`.
4. **V1 `LootTable` removed:** `rollLootTable`, `validateLootTables`, `convertLootToGameTable` (`src/loot/table.ts:1-141`, `src/tables/engine.ts:128-140`), and CLI `--loot` (`src/bin.ts:332, 786-855`) are deleted.
5. **Table schema bumped from `"2.0"` to `"3.0"`:**
   - Fractional/zero/negative/`NaN` weights (`weight: 0.25`, `1e-7`) are refused; `weight` must be a positive integer (`NonZeroU64`).
   - Every table requires `id` (was `table`), every entry requires unique `id`, and unknown fields (including dead `rollExpression` at `src/tables/schema.ts:88`, `minLevel`, `maxLevel`, `rarity`) are rejected.
   - `TableContext` (`level`, `triggerNat`, untyped `variables`) and `TableCondition` (`compare`, `nat`, string ordering) are replaced by typed `ContextValue` (`int`, `bool`, `text`) and explicit `IntCmp` / `TextEq` / `TextIn` / `BoolEq` / `HasTag` / `LacksTag` / `TriggerCmp` / `All` / `Any` / `Not`.
   - `rollGameTable(rawCollection, ...)` is replaced by `compileTables(raw)` $\to$ `CompiledCollection` passed to `rollTable` / `rollTableMultiple` / `analyzeTable`.
   - `rollTableMultiple` with `allowDuplicates: false` throws `InsufficientUniqueEntries` when `count > eligible.length` unless `policy: "truncate"` is passed.
6. **`roll-bridge` removed:** Binary `"roll-bridge"`, export `"@mcptoolshop/roll/bridge"`, `BridgeHandler`, and `src/bridge/*` are deleted.
7. **CLI flag & JSON output updates:** CLI transitions to subcommands (`roll <expr>`, `roll analyze <expr>`, `roll compare <a> <b>`, `roll table ...`, `roll verify ...`) while keeping top-level shorthand flags (`roll 2d6 --analyze`, `--at-least`, etc.) with strict numeric validation on `--at-least` (rejecting `"7abc"`, fixing `src/bin.ts:432`) and `method`/`caps` included in `compare --json`.

1. **`@mcptoolshop/roll@2.1.2` (immediate, from PR #11 `7191747`):** Ships the exact combined-modifier, engine-cap (`caps`), and divide-by-zero fixes on `main`, then cuts a `release/2.x` maintenance branch.

### 8.3 Migration guide outline (`docs/MIGRATION-3.0.md`)

1. **Who is affected at a glance:** Quick checklist (unseeded `roll()`/`analyze()` callers vs seeded tests, V1/V2 table authors, `roll-bridge` consumers, MCP hosts).
2. **Updating seeded rolls & adopting `RollReceipt`s:** Replacing `seededRng(number)` test snapshots, handling `bigint` seeds > $2^{53} - 1$, passing `RollAddress` for stateless replay, and calling `verifyReceipt()`.
3. **Die trace & error handling updates:** Mapping 2.x `DieResult.rerolledFrom` to 3.0 `DieTrace.rerolls`, catching structured `RollError` codes, and fixing expressions newly flagged by parse-time checks (`min > max`, `4dF!`, multi-group >10k dice).
4. **Upgrading V1 `LootTable` and V2 `GameTableCollection` JSON to Schema `"3.0"`:**

5. **Replacing `roll-bridge`:** Linking `roll-core` directly in Rust, importing `@mcptoolshop/roll` in Node/TS, or invoking `roll --json` from other languages.
6. **CLI & MCP changes:** Updated `--loot` $\to$ `roll table roll`, strict `--at-least` parsing, and new `seed`/`address`/`receipt`/`target_for` MCP tool arguments.

### 9.1 Cross-language conformance fixture suite (`fixtures/conformance/v3/`)

`roll-core` is the single source of truth. Running `cargo run -p roll-cli -- fixtures --out fixtures/conformance/v3/` deterministically generates six versioned JSON fixture files, gated in CI so neither Rust nor TypeScript can merge with uncommitted fixture diffs or a single mismatching test case:

1. **`01_kdf_and_rng.json`:**

2. **`02_grammar_and_ast.json`:**
   - Positive corpus (all 2.x valid expressions + fixed `1d20cscf`, `4d6khsa`, `2d6rsa`, `8d6r<2min2kh5sa`, `4dFr=-1`) $\to$ expected canonical string and serialized `Expr` AST.

3. **`03_rolls_and_receipts.json`:**
   - 500 end-to-end addressed expression and table rolls with exact canonical JSON `RollReceipt` byte strings and `receipt_sha256` digests.
   - 50 adversarial tampered receipts (mutated `raw_draws[0]`, appended extra unused draw word, altered `eligible_weight_total`, swapped `context` tag, wrong `collection_sha256`, mismatched `rules_version`) with the exact `ReceiptVerifyError` both Rust and TS must return.
4. **`04_exact_analysis.json`:**
   - Exact PMFs, `DistributionStats`, `ModelledCaps`, `cdf`, `targetForProbability` (`AtLeast` & `AtMost`), and `compare` verdicts across combined modifiers (`2d6r=1!`, `2d4ro=1min2!`, `3d4r=1kh2`), cap boundaries (`1d2!`, `1d100r<=99`, `1d6!>=1`, `1d6r>=1`), order-statistic DP (`10d20kh3`, `6d6dl1dh1`, `4d6!!kh3`), exploding pools (`8d6!cs>=5`, `10d6cf<=1`), exact multiplication (`(1d6)*(1d6)`), large-support `compare("100d100", "100d100")`, and divide-by-zero errors (`1d6/0`, `1d6/(1d2-1)`, `1d6/(1d100r<=99-50)`, `500d1000/(5d20-5)`, `(1d6/(5d20-5))+500d1000`).
   - **Two checks, kept apart.** (i) *Rust determinism:* the generated files are byte-identical across runs and between native and `wasm32-wasip1`, pinned by `MANIFEST.sha256` and the CI diff gate. This is a Rust-internal check, not the cross-language contract. (ii) *Cross-language values:* the TypeScript runner compares against the fixture values. Integer fields (`min`, `max`, `median`, `mode`, `percentiles`, `target_for`, reachable support keys, `caps`, method tags, Monte Carlo counts) must be equal. Probabilities (PMF entries, `cdf`, survival, `p_*`) must satisfy $|p_{ts} - p_{rust}| \le 10^{-12}$ (absolute: tiny tails cancel, so a relative or ULP bound is the wrong unit). Moments (`mean`, `stddev`, `entropy`, `mean_margin`) must satisfy $|x_{ts} - x_{rust}| \le 10^{-12} \cdot \max(1, |x_{rust}|)$. A different floating-point summation order is not a conformance failure.
   - **No knife edges.** Integer outputs that come from a float comparison (`median`, `percentiles`, `target_for`) are emitted only where the cumulative probability clears its threshold by more than $10^{-9}$. The generator skips any query point closer than that and records the margin, and the TypeScript runner asserts the margin too.
   - **Monte Carlo cases** are stored as integer counts per outcome plus `samples`, not as probabilities, so they do not depend on summation order.
   - **Fixture diffs are classified** in Rust CI: structural or integer changes (breaking) are reported apart from float changes, with the largest absolute and relative move, so an intended algorithm change shows up as a numeric-only diff that a reviewer can accept knowingly.
5. **`05_tables.json`:**

### 9.2 Property tests (`proptest` 1.12.0 in Rust & Vitest in TS)

1. **Receipt round-trip & tamper soundness:** For arbitrary `(RollAddress, valid Expr | CompiledCollection + TableContext)`, `let json = to_canonical_receipt_json(&receipt);` parses back via `verify_receipt_json(&json, tables)` with `Ok(receipt)`, re-serializes to byte-identical `json`, and mutating any single field or truncating/extending `raw_draws` yields `Err(RollError::ReceiptInvalid(_))`.
2. **Parser canonical idempotence:** For arbitrary generated `Expr` trees, `parse(&expr.to_canonical_string()) == Ok(expr.clone())`.
3. **Sampling without replacement invariants:** For arbitrary tables with $K \in 1..=25$ eligible entries of arbitrary `NonZeroU64` weights (spanning $1$ to $10^{15}$) and $c \in 1..=K$:
   - `entries.len() == c` (never comes back short);
   - `entries.iter().map(|e| &e.entry_id).collect::<BTreeSet<_>>().len() == c` (strictly unique);
   - `step_weights[0] == total_eligible_weight` and `step_weights[t] == step_weights[t - 1] - weight(chosen[t - 1])` for all $1 \le t < c$;
   - On 3-entry small tables ($K = 3, c = 2$), empirical pair frequencies $(i, j)$ over 50,000 draws match exact ordered Wallenius/sequential probability $\frac{w_i}{W} \cdot \frac{w_j}{W - w_i}$ within Kolmogorov–Smirnov/chi-square bounds.
4. **PMF conservation & query identities:** For every exact `AnalysisReport`:
   - Every $(v, p)$ has $p \ge 0$, strictly ascending $v$, and $\left|\sum_v p - 1.0\right| \le 10^{-12}$;
   - For every $x \in [\text{min} - 1, \text{max} + 1]$, `prob_at_most(x) + prob_at_least(x + 1)` equals total mass within $10^{-12}$, and `prob_in_range(a, b) == prob_at_most(b) - prob_at_most(a - 1)`;
   - For every $p \in \{0.01, 0.10, 0.25, 0.50, 0.75, 0.90, 0.99\}$, `t = target_for_probability(p, AtLeast)` satisfies `prob_at_least(t) >= p - 1e-12` and (when $t < \text{max}$) `prob_at_least(next_support_val(t)) < p + 1e-12`.

### 9.3 Exact-vs-brute-force prefix-tape oracle on small dice

Generalizing PR #11's `runAdaptivePrefixOracle` (`tests/analyze-correctness.test.ts:331-408`), `roll-core` includes a black-box prefix-tape tree evaluator that drives the **real** `evaluate_with_rng` over exhaustive uniform face branches `(0..span)` with zero knowledge of modifier stages:
- Sweeps small dice expressions ($N \in 1..=4$, sides $\in \{2, 3, 4, 6, \text{Fate}\}$, single and combined modifiers across `r`, `ro`, `min`, `max`, `!`, `!!`, `!p`, `kh`, `kl`, `dh`, `dl`, `cs`, `cf`, plus binary `+ - * /` combinations including `1d6/(1d2!-22)`).
- On finite-tree expressions (`ro`, `min`/`max`, `kh`/`dl`, `cs`/`cf`, `1d2!` up to `MAX_EXPLOSIONS + 1` draws, `1d2r=1` up to `MAX_REROLLS + 1` draws), `tail_mass == 0.0` and every support probability matches within `1e-14`.
- On infinite-branching capped expressions (`2d6r=1!`, `3d4r=1kh2`), adaptive tree expansion runs to `tail_mass < 1e-7` and asserts `p_exact(k) + 1e-13 >= p_oracle(k)` and `|p_exact(k) - p_oracle(k)| <= tail_mass + 1e-12` at every integer $k$.

## 10. What we have not thought to ask, and the top three risks

### 10.1 What we have not thought to ask

1. **Public-beacon predictability vs hidden information in *Merchant League*:**
   - A game can roll directly from a pre-named `drand` round and use replayable routes and rolls to tell force majeure from deliberate breach. Because `RollAddress` + `drand` randomness are **public**, *every player at the table can also compute what any caravan would have rolled on every unchosen road, or compute a rival caravan's road event before that rival announces it if routes are hidden under sealed moves!*
   - **Design implication to settle before the game's turn resolution is built:** Public `RollAddress`es over raw `drand` randomness are ideal for **public-knowledge phase rolls** (open roads, town market shocks, public force-majeure audits), whereas **fog-of-war / private rolls** MUST bind a committed secret (e.g., `SHA-256(drand_randomness || sealed_move_salt)` passed as `SeedMaterial::Bytes32`) so rivals cannot brute-force a player's hidden outcome from the public beacon alone, while still allowing $O(1)$ receipt verification once the sealed move is revealed.
2. **Content-addressed table archiving across mid-chapter balance patches:**
   - A game that runs multi-week chapters with mid-chapter edicts will change tables while receipts are live. If an event table is patched or an edict added mid-chapter, `collection_sha256` changes. A player re-checking a Day 3 receipt on Day 10 will fail `verify_receipt` with `CollectionHashMismatch` unless the indexer or client archives immutable `CompiledCollection` JSON blobs indexed by `collection_sha256` (not just the latest `tables.json` on disk).
3. **Should `RollReceipt` commit to *negative* / unrolled eligibility, or can table descriptions change without invalidating hashes?**
   - If designers fix a typo in `entry.description` mid-season, hashing the entire raw `RawTableCollection` changes `collection_sha256`. Computing `collection_sha256` over a **canonical rule projection** (table IDs, `allow_duplicates`, entry IDs, `NonZeroU64` weights, `action`, and `conditions` — excluding cosmetic `description` and `metadata`) lets writers fix prose typos without breaking receipt hashes for an active chapter. Recommend adopting this rule-projection hash in Section 6.2.
4. **Dynamic context-scaled weights vs table proliferation:**
   - Static `NonZeroU64` weights are clean and receipt-friendly, `[Guess]` but if road ambush odds scale continuously with caravan wealth or winter severity (`1..10`), designers may end up duplicating tables per tier unless an optional bounded integer weight multiplier (`base_weight * clamp(var, 1, 100)`) is supported in 3.1. Recommend shipping **static `NonZeroU64` only in 3.0** and measuring table duplication in the first playtest.
5. **CLI `site/` documentation sync & V1 handbook drift:**
   - At the 2.x reference commit, CI never builds or audits `site/`, and `site/src/content/docs/handbook/api-reference.md` still documents V1 `DiceNode` types. The Roll 3.0 release must include `site/` updates and wire `npm --prefix site run build` into `.github/workflows/ci.yml`.

### 10.2 Top three risks

1. **Subtle semantic drift between `roll-core` (Rust) and `@mcptoolshop/roll` (pure TypeScript port):**
   - *Failure mode:* Signed 32-bit bitwise shifts in JS (`<<` / `|` coerce to signed `i32` unless `>>> 0` or `BigInt` is used), `BigInt` floor division sign edge cases on negative divisors, UTF-8 vs UTF-16 sorting on non-ASCII `TableContext` keys in canonical JSON, or `f64` catastrophic cancellation in order-statistic DP.
   - *Mitigation:* `roll-core` generates `fixtures/conformance/v3/` directly in CI (never hand-written), including bit-level KDF/ChaCha12/Lemire slow-path vectors, tampered receipts, negative division cases, and UTF-16 surrogate-pair context keys (`U+1F3B2` `"🎲"` vs `U+E000`, where UTF-8 order and UTF-16 order invert!). Release publishing is blocked unless both `cargo test` (native + `wasm32-wasip1`) and `npm run verify` pass against the identical fixture SHA-256 manifest.
2. **State explosion in DAG `analyze_table` and wide-range order-statistic DP:**
   - *Failure mode:* An acyclic table collection with 15 chained diamond layers ($2^{15} = 32,768$ paths) stalls `analyze_table` if expanded as a tree, and an expression like `200d1000kh100` stays under `MAX_ANALYZE_DICE = 1_000` while requiring $\sim 1000 \times 200 \times 100,000 \approx 2 \times 10^{10}$ DP transitions if gated only on final support size ($99,901 < 10^7$).
   - *Mitigation:* Enforce topological bottom-up memoization per `table_id` in `analyze_table` (bounding work linearly in DAG edges) and gate the order-statistic DP on **accumulated inner-loop transitions** (`<= MAX_EXACT_STATES`), not just output map cardinality, before allocating each step's map.
3. **Receipt verification fragility from coupling `engine_version` or cosmetic table text to replay semantics:**
   - *Failure mode:* Bumping `roll-core` from `3.0.0` to `3.0.1` for a CLI formatting fix or fixing a typo in an event table's flavour text causes old receipts to fail verification if verifiers check `engine_version` equality or hash cosmetic fields.
   - *Mitigation:* `verify_receipt` dispatches strictly on `schema_version` (`"roll.receipt.v1"`) and `rules_version` (`"roll.v3"`), treats `engine_version` as passive provenance data inside the signed envelope, and defines `collection_sha256` over canonical rule-bearing table fields only.
